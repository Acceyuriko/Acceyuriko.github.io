[chunmao](https://github.com/Acceyuriko/chunmao) 是一个运行在群聊消息链路上的机器人服务。它最初大概属于那种“这个小功能顺手加一下”的项目，后来小功能们互相拉帮结派，欢迎语、问答、复读、周报、角色查询、车车流程和图片生成全都住了进来。于是问题变成了：怎样让它继续加功能，却不把整个机器人变成一条巨大的 `if...else`？

我最后选择把它拆成接入、分发、数据模型、定时任务和外部服务几个层次。它不算庞大的平台，但足够完整地展示了一个群聊机器人最容易踩到的坑：重复事件、平台差异、异步回调、半截失败和“文字能说清，图片更适合发出来”的产品取舍。_(:з」∠)_

## 一条消息的旅程

服务使用 Express 提供 `/notify` 接口，接收 OneBot 风格的事件。收到请求后，消息服务先确认事件是不是自己发出的，再检查黑名单、消息类型和是否已经处理过，最后才进入命令匹配和业务逻辑。

```text
OneBot 事件
    ↓ POST /notify
Express 路由 / MessageService
    ├─ 事件去重、机器人自身过滤、黑名单
    ├─ @ / 名称 / 命令前缀判断
    ├─ Sequelize / SQLite 查询与更新
    ├─ 外部接口或 Puppeteer 图片渲染
    └─ 定时统计与业务状态
    ↓
CQ HTTP API → send_group_msg → 群聊
```

最后的发送通过 CQ HTTP API 完成。业务层不需要直接操作 QQ 客户端，只需要构造文本、@、图片等消息段；入口层负责调用 `send_group_msg`。这层抽象看起来薄薄的，却让命令逻辑不会被某个具体 QQ 客户端的调用方式绑死。

## 群消息不是普通的 HTTP 请求

HTTP 接口很容易让人产生一种错觉：请求来了，函数执行完，事情就结束了。群聊环境完全不是这样。上游可能重试同一个事件，机器人可能收到自己刚刚发出的消息，群友可能同时触发多个耗时操作，某个外部 API 也可能在图片已经生成一半时超时。

`MessageService.handle` 会维护最近处理过的消息 ID，最多保留约 1024 条，用来避免同一事件重复消费。它还会根据 `post_type` 和消息子类型判断这是普通群消息、入群通知、发送回执，还是其他事件，不会把所有事件都当作“有人说了一句话”。

过滤顺序也很有讲究：先做不需要数据库的便宜判断，再做命令匹配，之后才进入数据库查询和外部请求，最后才启动 Puppeteer 这种成本更高的操作。这样至少不会因为一条机器人自己的回执，启动一整个浏览器进程。机器人开发里很少有真正的魔法，更多是把昂贵的事情尽可能往后放。

## 触发方式：既要明确，也要允许一点松弛

命令可以通过机器人名称或 @ 触发，进入明确的命令分支；部分问答则允许不加前缀，直接查询 `MsgNoPrefix`。问答匹配不是只做完全相等，还会进行包含匹配和 Levenshtein 距离判断，群友不必每次都精准复刻数据库里的原句。

这种“确定入口 + 有限模糊”的组合比较适合群聊：会改变数据或触发复杂动作的命令需要明显的触发方式，轻量问答可以稍微宽松一点。模糊匹配的范围不能无限放大，否则机器人会变成一个过于热心、到处插话的群成员——而且还是无法禁言的那种。

当前命令包括欢迎消息、角色和联盟查询、绑定信息、问答学习、星力查询、复读统计、复读周报，以及“叫车、发车、到站”等群内流程。不同命令背后连接的模型和外部服务各不相同，统一入口的价值就在于让它们共享过滤、日志和错误处理，而不是共享一锅粥。

## SQLite 和 Sequelize：小机器人也需要数据边界

项目使用 Sequelize、`sequelize-typescript` 和 SQLite。模型分别覆盖消息问答、无前缀问答、复读消息、复读用户、排行信息和车队状态等数据；`migrations/` 记录表结构变化和唯一约束，避免每次升级都靠手动改数据库。

复读功能尤其能说明“状态”和“事件”的区别。它不是简单地看到同一段文字就加一，服务需要按群保存消息序列，并确认是不是不同成员连续重复；相同成员连续发出的内容不能和多人接龙混为一谈。`task.service` 再按 ISO 周统计最长复读链和成员排行，生成周报。

数据落库后，Node 进程重启并不会把历史清空。对于一个看似玩具的群机器人来说，这已经很重要：今天的复读榜、上周的问答和当前车队状态，都不应该因为进程更新就凭空失忆。

## 文字说不清的时候，让 Puppeteer 出场

角色排行、联盟信息和周报如果全部塞在一条长消息里，群里很快就会变成一堵字墙。`draw.service` 使用 Puppeteer 打开 HTML 模板并截图，把表格、排行、时间和装饰统一排版成图片，再由 `message.service` 组装 CQ 图片消息。

这里的关键是把数据和视觉分开：业务服务负责查询“谁排第几”，模板负责“第几名应该长什么样”。如果以后要改颜色、增加字段或适配手机宽度，不需要回头改命令解析器。代价也很明确：启动浏览器比拼一段字符串重，页面渲染失败时还要记录临时文件和错误上下文，所以这类能力应该放在真正需要它的命令里。

## 当 OneBot 不再是唯一入口

QQ 侧的接入方式变化后，我又做了 [chunmao-ll](https://github.com/Acceyuriko/chunmao-ll)，作为 LiteLoaderQQNT / Electron 适配层。它在 Electron 主进程中 Hook QQNT 消息事件，把 QQNT 的文本、@ 和图片元素转换回机器人熟悉的 CQ 风格；机器人发送消息时，再把 CQ 消息转换成 QQNT 的消息元素。

两个服务通过本地 HTTP 保持边界：插件监听 5700 端口，原机器人继续在 6624 端口接收通知。这样平台变化被压缩到适配器里，chunmao 的问答、复读和统计逻辑无需跟着 QQNT 的内部事件结构一起重写。

适配器需要处理的细节比“把文本转发一下”多得多。图片要通过 QQNT 文件 API 获取类型、MD5 和目标路径；@ 消息要结合群成员缓存映射账号信息；异步 `ntCall` 的返回值要通过 UUID 放入待处理 IPC 回调表，再交给发起请求的逻辑。插件还提供 `/send_group_msg` 和 `/get_group_member_list` 等本地 Express 接口，继续模拟原有的 CQ HTTP 边界。

## 如果我要再加一个命令，会先经过什么

一个新命令通常要经过这条小流程：先确定触发方式，再定义输入和权限；然后决定是否需要新模型或迁移；接着把业务逻辑放进服务层，最后把返回结果转换成文本、@ 或图片消息。看起来只是“加一个分支”，实际上还要考虑重复事件、数据库失败、外部 API 超时和消息发送失败。

我会尽量让命令处理函数保持短一些，把查询、统计和图片渲染拆到各自的 service。入口层只做识别和编排，模型层只关心数据，`cq.service` 只负责和发送接口说话。这样新增命令时，修改范围可以被限制在几个清楚的文件里，不会因为一个周报功能改坏欢迎消息。

命令的返回值也最好先形成一个内部消息结构，再在最后一步转换为 CQ 段。纯文本、@、图片和多个消息段的差异就不会散落在每个命令里；以后更换接入适配器时，也只需要重写转换层。

## 去重不是“存一个 ID”这么简单

消息 ID 的缓存解决的是短时间重复投递，但它不能替代业务幂等。比如一条学习问答可能已经写入数据库，却在发送回复前进程崩溃；上游重试后，第二次请求应该避免再次插入同一条学习记录，同时又要决定是否重新发送回复。

因此可以把处理过程分成“收到事件、完成业务写入、生成回复、发送回复”几个阶段记录。内存里的最近 ID 适合挡住普通重复事件，数据库里的唯一约束和业务状态则负责更长生命周期的重复。机器人越往后加功能，越需要区分这两层，不然一次网络抖动就可能变成两条记录、两张图片和两份周报。

## 日志和错误：失败也要能被看见

Webhook 处理经过 Express 错误中间件，异常写入 Winston 日志，并返回 500，让上游知道这次处理没有完成。这个返回码很重要：如果渲染失败却返回成功，上游可能不会重试，群里也只会安静地少一条结果；如果所有错误都吞掉，排查时就只能问“刚才是不是没反应”。

当然，返回 500 也不是万能的。一个消息是否已经写入数据库、图片是否已经落盘、发送 API 是否成功，都需要在日志和状态设计里说清楚。对于异步机器人，真正麻烦的往往不是抛出异常，而是异常发生在“已经做了一半”的时候。

## 我为什么还觉得这个项目有意思

chunmao 不是一个宏大的 AI 平台，它更像一个群聊生活的缩影：需求来自一句随口的“能不能查一下”，最后却会碰到数据库迁移、幂等、模糊匹配、浏览器渲染、平台适配和异步协议。把这些小问题一个个收好，才让机器人从“能回复”变成“可以长期运行”。

如果以后再加功能，我最希望继续保持的不是命令数量，而是每个功能都能说清楚自己的输入、状态、输出和失败方式。至于群里会不会因此更热闹——这个就交给群友决定啦 (｀・ω・´)

## 平台适配真正隔离的是什么

`chunmao-ll` 的价值不只是“把 QQNT 消息转发到 5700 端口”。它把平台内部事件、消息元素、文件路径和 IPC 回调，翻译成机器人已经理解的 HTTP / CQ 语义。换平台时变化的是适配器，不是“复读统计按周计算”这类业务规则。

这个边界也让故障更容易定位：如果 `/notify` 根本没有收到请求，先看插件事件 Hook 和本地 HTTP；如果请求到了但没有回复，再看 `MessageService`、数据库或外部渲染；如果回复创建成功却发不出去，最后检查 CQ API 和 QQNT 的发送转换。把问题按边界分层，群里那句“机器人又没反应了”才有机会变成可执行的排查步骤。
