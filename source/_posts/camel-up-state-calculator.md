[CamelUpStateCalculator](https://github.com/Acceyuriko/CamelUpStateCalculator) 是一个给《骆驼快跑》使用的状态计算器。输入当前棋盘上的骆驼位置、叠放顺序、陷阱以及还没有掷出的骰子，工具会枚举当前小回合结束后每只骆驼处于第 1、2、5 名的概率。

桌游里经常出现这样的瞬间：大家都说“这只看起来要赢了”，但白骆驼、黑骆驼、叠放顺序和陷阱一起搅进来以后，直觉就开始打滑。这个项目不替玩家下注，也不假装自己知道最佳策略，它只做一件很具体的事：把规则允许的后续状态算出来。_(:з」∠)_

## 先把棋盘变成能计算的状态

棋盘被表示为长度为 20 的格子数组，每个格子保存当前位置上的骆驼数组。红、黄、绿、蓝、紫是玩家骆驼，白、黑是特殊骆驼；数组顺序表示叠放关系，而不是一个可以随便忽略的附加字段。陷阱则用 `+1` 和 `-1` 表示不同方向的影响。

```text
camelIndex[格子位置] = [下方骆驼, ..., 上方骆驼]
```

因此，移动一只骆驼时不能只把它的坐标加上步数。如果目标骆驼上面还压着其他骆驼，整叠都要一起移动；落点已有骆驼时，新的一叠又要按照规则插入正确位置。白、黑骆驼的移动方向和普通骆驼不同，陷阱还会改变步数或叠放位置。

状态建模如果在这里偷懒，后面的概率再精确也没有意义。一个“数组顺序搞反”的小错误，可能让整张概率表看起来很合理，却与桌面上的真实规则完全相反。

## `move`：把复杂规则集中在一个纯函数里

`iterator.js` 的核心是 `move` 和递归 `iteration`。`move` 先深拷贝当前状态，找到目标骆驼所在的格子，再取出目标骆驼和它上方的整组。落点为空时创建新数组；落点已有骆驼时，根据正向、反向、是否触发陷阱以及特殊骆驼规则，决定插入头部、尾部或第一个玩家骆驼之前。

把这些规则集中在一个纯函数里有两个好处：第一，输入状态不会被递归分支互相污染；第二，规则出错时可以单独测试移动，而不用先跑完整的概率枚举。递归只负责“选择哪枚骰子、走几步、下一个状态是什么”，不需要同时理解叠骆驼的全部细节。

这也是我处理桌游规则时很喜欢的做法：先把现实里的动作写成一个状态转换，再让搜索算法在这些转换上工作。只要 `move` 可信，后面增加 UI、Worker 或概率统计都不会重新发明规则。

## 枚举而不是随机模拟

每枚彩色骰子有 1、2、3 三种步数，代码用 `ratio: 2` 表示相应的骰面权重；白、黑骰子则分别展开白骆驼和黑骆驼的三种步数。递归每次从剩余骰子里选择一枚，展开它的可能结果，直到所有骰子都处理完成。

```text
当前状态 + 剩余骰子
          ↓ 选择一枚骰子
       1 / 2 / 3 步（或白 / 黑骆驼）
          ↓
        move 生成新状态
          ↓
      递归处理剩余骰子
          ↓
      最终状态统计名次
```

代码不是随机抽取几千次结果来估计概率，而是完整枚举所有可能的小回合状态。最终每个骆驼的计数除以 `totalState`，得到可以直接显示的小数概率。同一输入每次得到相同结果，规则变化也可以通过对比完整状态数来检查。

完整枚举的代价是状态空间会迅速变大。好处是结果可复现、没有随机误差；坏处是浏览器主线程很快会忙到无法点击按钮。于是项目的下一步不是马上改成近似算法，而是把相同的计算搬到 Web Worker。

## 名次统计：叠放顺序决定最后的答案

统计最终状态时，程序按棋盘格子从前往后遍历，再按照叠放数组从上方到下方遍历。白、黑特殊骆驼参与移动，但最终名次统计只记录五只玩家骆驼的第 1、2、5 名。

这一步容易写成“按坐标排序然后取前三”，但《骆驼快跑》的叠放规则让同一格上的骆驼不能被当成平局。前方格子优先，位于同一格时上层关系又决定先后；如果忽略它，特殊骆驼移动带来的影响就会在最后一步消失。

输出结构保留每只骆驼的计数和 `totalState`，主线程再把它们转换为概率并展示。保留计数而不是只传小数，方便调试：当两个结果不同的时候，可以继续追问究竟是状态总数变了，还是某一只骆驼命中的终局数变了。

## 为什么一定要用 Web Worker

完整展开时，主线程如果直接递归计算，页面会停止响应。用户点击了骰子，浏览器却像是在思考宇宙的终极问题一样迟迟没有反应。Worker 可以让计算在后台线程执行，主线程继续负责修改状态、显示加载中和更新结果。

当任务量足够大时，项目还会继续拆分第一层。六枚骰子都可用时，第一层大约有 21 个分支：五枚彩色骰子各展开三个步数分支，白、黑骰子则分别展开对应骆驼的三个步数分支。主线程根据 `navigator.hardwareConcurrency` 创建多个 Worker，把任务分发出去；某个 Worker 完成后继续领取下一个任务。

每个 Worker 只返回 `stateCount` 和 `totalState`，不把巨大的中间状态树传回主线程。主线程合并各分支计数，统一转换为概率并更新 Ant Design 表格。这样做不仅降低通信量，也把 UI 和枚举逻辑的责任分清楚了。

Worker 通信也有实际成本：初始棋盘和剩余骰子需要序列化，任务拆得太细会让消息传输抵消并行收益，任务拆得太粗又会让部分 Worker 提前闲下来。因此项目只在第一层拆分较大的分支，让每个 Worker 在本地完成更深的递归，再返回很小的计数结果。这是浏览器并行计算里很典型的取舍：不是 Worker 越多越快，而是计算量和通信量要保持比例。

## 并行不会改变概率模型

把第一层拆成多个 Worker 只是改变执行顺序，不会改变每个分支的规则和权重。每个分支仍然从同一个初始状态出发，使用同样的 `move` 和递归逻辑；最终只是把多个计数相加。

这点很重要，因为并行化最怕悄悄引入另一套逻辑。如果某个 Worker 使用了不同的深拷贝方式、漏算了一枚骰子，结果可能只在特定输入下偏掉。项目选择让 Worker 做相对纯粹的枚举，把状态合并和概率转换留在一个地方，就是为了减少这种分叉。

## 状态树为什么会迅速变大

每一层递归都要选择一枚尚未使用的骰子，再展开它的步数或特殊骆驼分支；下一层又从剩余骰子中选择。这里既有“选择哪一枚”的排列，也有“这一枚掷出几步”的分支，最后还要把叠放关系传播到终局。状态数量增长得很快，不能把每个中间状态都保存下来等待最后处理。

所以 `iteration` 更像一台深度优先的计数器：生成一个状态，继续向下递归，到了终局就把相关名次计数加一，然后返回并释放这条分支。它只保留当前路径需要的状态，避免把完整状态树堆在内存里。深拷贝虽然有成本，却能保证兄弟分支不会互相改写；对这种规则复杂、结果需要可信的工具，先保证状态隔离比过早追求微优化更重要。

骰面权重也不能被忘记。普通骰子不同步数的概率、白黑特殊骰子的分支，都要以同一套计数约定进入 `totalState`。如果只把分支数相加，却没有同步分母，最后得到的数字看起来仍然像概率，实际上已经失去解释。

## 怎样用小例子验证规则没有写反

完整枚举很适合做确定性测试。可以先构造只有一枚剩余骰子的局面，手工列出 1、2、3 步后的落点；再构造一个落点有叠骆驼的局面，检查目标骆驼上方的整叠是否一起移动；最后加入白、黑骆驼和正负陷阱，逐步比较 `stateCount` 与手算结果。

这些小局面比直接拿一盘复杂棋局看最终百分比更容易定位问题。若最终结果不对，先问 `move` 是否产生了正确的新棋盘，再问递归是否漏了骰子，最后才检查名次统计和概率转换。把规则、枚举和展示分成三段，调试路径会短很多。

## 浏览器工具的界面也要尊重规则

页面使用简单的 HTML 入口和浏览器端脚本，运行时加载 React、Ant Design、Lodash 等依赖。用户可以输入每个格子的骆驼、陷阱位置和可用骰子，然后触发计算并查看结果。没有服务端、没有数据库，项目可以直接部署到静态托管。

状态输入界面其实和算法同样重要：如果骆驼叠放顺序不容易表达，用户就会在输入阶段把状态填错；如果加载状态不明显，就会误以为按钮没有反应；如果结果只显示一串百分比，却不说明是哪个剩余骰子集合，也很难复核。一个概率工具必须让“输入是什么、计算了什么、结果意味着什么”都尽量可见。

## 这个项目最后算出来的是什么

它算的不是“这局一定押哪只”，而是一个固定局面、固定剩余骰子集合下的条件概率。改变一枚骰子、移动一个陷阱、调整一叠骆驼的位置，重新计算后，概率变化就有了可以追踪的来源。

对我来说，这个项目最有意思的地方，是把桌游里非常具象的东西——骆驼、格子、叠放、陷阱——翻译成纯函数、递归树、计数器和 Worker。规则没有因为变成代码而变简单，但至少它们变得可以被逐步检查。至于最后下注哪只？那还是留给桌边的人类吧 (｀・ω・´)

如果把这个工具再往前推一步，我会增加“展开某个结果”的调试视图：用户点击一只骆驼的概率，就能看到它命中的终局数量、相关骰子分支和典型移动路径。概率表告诉你结果，路径视图则告诉你结果从哪里来；对桌游这种规则密集的问题，两者放在一起会比一个更大的百分比更有说服力。
